SPEC

his · database

SQLite（node:sqlite）アクセス層に Kysely を導入するための仕様とプラン。

Overview

採用: Kysely（型安全クエリビルダ, ORM ではない）+ kysely-sqlite（node:sqlite dialect）。行/テーブル型を生成し、FTS5・集計・PRAGMA などは sql テンプレートで生 SQL を維持する。

目的

列/テーブル参照のコンパイル時検証、リファクタ追従、as unknown as T[] の排除。DB 型を生成し Kysely<DB> に通す。

範囲

core/src/db/** と sync のクエリ。既存 migration も Kysely Migrator へ全面移行（user_version ランナーは廃止、版スタンプとしてのみ残置）。

非対象

スキーマ設計変更、ORM 的なリレーション、生 SQL の全面禁止。down migration は必須にしない（forward-only 維持）。

最大の影響

Kysely の API は 非同期（Promise）。データ層が async 化し、handler / CLI / sync / テストへ波及する（下記 R1）。

Dependencies

core に runtime 依存が2つ増える（これまで runtime 依存ゼロ）。

Dialect & lifecycle

公式 node:sqlite dialect は無い。kysely-sqlite が事実上の移植版（nikeee, 公式 SQLite dialect を driver だけ差し替え）。既存の DatabaseSync を注入して使う。 

import { Kysely } from 'kysely'
import { SqliteDialect } from 'kysely-sqlite'
import type { DB } from './schema.ts'

// open() が張った DatabaseSync をそのまま渡す（単一 writer を維持）
export function createDb(handle: DatabaseSync): Kysely<DB> {
  return new Kysely<DB>({ dialect: new SqliteDialect({ database: handle }) })
}

Pragmas

WAL / foreign_keys / busy_timeout は既存 open() のまま。pre-configured な handle を渡せば dialect の onCreateConnection は不要。

Close の一本化

kysely.destroy() は handle を close する。lifecycle をどちらが持つか決める（推奨: Kysely が所有、close は destroy() のみ）。

dialect は同期 handle を Promise で包み、mutex で直列化する。トランザクションは db.transaction().execute()、または既存の raw BEGIN/COMMIT を維持。

Type generation

採用: kysely-codegen（programmatic API）。generate({ db, dialect }) に kysely-sqlite の Kysely を渡すため native 依存を作らない。自作（案 B/C）は様子見。

scripts/gen-db-types.ts

import { DatabaseSync } from 'node:sqlite'
import { generate, getDialect } from 'kysely-codegen'
import { createDb, migrate } from '../src/db/db.ts'

// migration 適用済みの :memory: に対して生成（driver は node:sqlite）
const handle = new DatabaseSync(':memory:')
await migrate(handle)                 // Kysely Migrator
await generate({
  db: createDb(handle),
  dialect: getDialect('sqlite'),
  outFile: './src/db/schema.ts',
  excludePattern: '{urls_fts*,kysely_migration*}',
  verify: process.argv.includes('--check'),
})
  • 出力先: core/src/db/schema.ts（生成物・手編集禁止）
  • scripts: "db:gen" = node scripts/gen-db-types.ts / "db:check" = 同 --check（verify で再生成せず差分検知、CI 用）
  • 型対応: codegen 既定（INTEGER→number 等）。EpochMs = number、boolean は INTEGER(0/1) → number
  • 除外: FTS5 仮想テーブル urls_fts（+ shadow）と kysely_migration*（micromatch glob）
  • PK の null 扱い: SQLite は INTEGER PRIMARY KEY を nullable と報告するため、DDL に NOT NULL を明記して回避（overrides 不要）

手順

  1. migration を編集/追加: core/src/db/migrations/NNN_name.ts（export async function up(db)）
  2. 再生成: pnpm --filter @his/core db:gen → core/src/db/schema.ts を更新
  3. 生成物をコミット（手編集しない）
  4. 検証/CI: pnpm --filter @his/core db:check（差分があれば fail）
  5. 型チェック: pnpm -r typecheck（webui は tsc -b）／lint: pnpm -r lint

Migrations & queries

採用: Kysely Migrator（kysely/migration の Migrator + FileMigrationProvider）。既存の PRAGMA user_version ランナーは廃止し、追跡を kysely_migration / kysely_migration_lock に移す。user_version は旧ランナー互換の版スタンプとしてのみ継続（成功後 8）。

形式・順序・追跡

各 migration は NNN_name.ts で export async function up(db)（down? 任意）。適用は migrator.migrateToLatest()（async）。順序は名前の alpha-numeric（NNN_ 維持）。適用済みは kysely_migration に記録、並行実行は lock で直列化。

生 SQL を残す箇所

DDL は FTS5 仮想テーブル / トリガ / partial index が主で builder では表現不可 → migration は sql テンプレート中心。クエリ側も FTS の MATCH join・集計・PRAGMA・HIDDEN_URLS_EXCLUDED は raw 維持。

移行時の論点 H = Hurdle

H1 複数文スクリプト

既存 .sql は複数文（000 は表 + index + FTS + トリガ）。Kysely の sql は 1 文単位 → 文ごとに sql\`…\`.execute(db) へ分割移植（CREATE TRIGGER …BEGIN…END は1文なのでそのまま）。

H2 FK トグル（004） squash で解消

PRAGMA foreign_keys はトランザクション内では no-op。Migrator は既定でトランザクションを張るため、FK off を要する 004 の作り直しが動かない。

採用（H2-d）: 履歴を squash。 000〜006 を 1 本の 000_init.ts に畳み、004 の FK 作り直しごと消す。000 が既に最終形（browser/profile/UNIQUE を含む）なので畳める。既存 DB は user_version を検出して kysely_migration に baseline 挿入（init を再実行しない＝データは不変）。baseline は最新まで適用済み（user_version == 7）の DB のみ。途中版は先に旧ランナーで最新化してから baseline。
migrate() 成功後に PRAGMA user_version = 8（= legacy 7 + 1）を刻む。旧ランナーは while (version < 7) なので 8 は no-op になり、新規作成した DB を旧リリースへロールバックしても init を再実行しない。baseline は INSERT OR IGNORE で冪等（同時初回オープンの UNIQUE 衝突回避）。user_version > 7 は Kysely 管理下として素通し。
H2 の代替（不採用）: (a) supportsTransactionalDdl:false（原子性喪失）、(b) 004 を FK 非依存に再設計、(c) 004 のみ Migrator 外で実行（順序/追跡が煩雑）。
H2 の候補: (a) adapter を supportsTransactionalDdl: false にしトランザクション無しで走らせる、(b) 004 を FK 非依存の手順へ再設計、(c) H2 相当のみ Migrator 外で個別実行。いずれも原子性/移植コストのトレードオフ。
Kysely の API は非同期。initDb（migration 適用）・search / stats / getItem / settings / applyVisits が Promise 化する（Plan Phase 6）。

Risks & open questions

R1 async 化の波及

Kysely は常に Promise。データ層が async になり core→server→cli→tests に波及する。最小化は不可（同期モードは無い）。

R2 dialect の成熟度

公式ではなくコミュニティ移植（kysely-sqlite）。仕様変更を追う必要あり。

R3 node:sqlite

比較的新しく API が動きうる。Node 下限（^22.16/>=23.11）を固定。

R4 型マッピング

INTEGER の boolean/epoch は number になる。必要列のみ override し、EpochMs は別名で維持。

R5 混在スタイル

FTS/集計は raw のため builder と sql が混在。方針を明文化して一貫させる。

R6 migrations 移行

Kysely Migrator へ全面移行（user_version ランナー廃止＝版スタンプのみ残置、kysely_migration へ）。000〜006 は squash して 000_init.ts に（H2 解消）、既存 DB は baseline で再実行回避、成功後 user_version = 8 でロールバック安全化。H1 は文分割で対応。

Background & links

Kysely に node:sqlite の公式 dialect は無い。API 差異（reader 不在 → columns().length、パラメータ spread）を吸収する移植版のうち、公式 better-sqlite3 dialect を流用し既存 handle を注入できる kysely-sqlite を採用。codegen は kysely-codegen の programmatic API（generate）に kysely-sqlite の Kysely を渡し、native 依存を回避。
